# CLAUDE.md

Engineering guide for Claude Code working in this repository. The product specification is
[`docs/spec.md`](docs/spec.md); the user-facing documentation is
[`docs/user-guide.md`](docs/user-guide.md) and [`docs/configuration.md`](docs/configuration.md).
This file is the part that is not in either: the standing constraints, and a long list of
traps that each cost a real defect.

## Current state

VADD runs real objectives end to end: a project is registered or cloned, an objective in any
of the three modes drives an agent through the full machine in its own worktree, verification
runs for real, and integration squashes, keeps or discards. Both adapters (Claude Code, Codex)
work. Every screen in `packages/web` has been opened in a real browser at 1440/820/600.

**One gate is deliberately red.** `pnpm eval` exits non-zero by design: `decision_needed`
scores 100.0% precision and recall, `evidence` 75.0% precision against a 90% bar. **Do not
relax it, re-scope it, or lower its bar; and do not edit a label file to close the gap** —
the labels are the human's to author from blind transcripts. What it is waiting on is an
independent re-labelling and a corpus past ten transcripts. CI runs it non-blocking.

Two standing caveats worth carrying into any pass:

- Every gate number rests on labels blind-drafted *inside* the recording sessions, not
  independent ones, so a cleared gate on them would be worth less than it looks.
- The frozen corpus was recorded before `memory_note` and `artifact` existed, so anything
  touching those two event types or the `permits` mechanism is **unmeasured** by the gate,
  not merely unchanged by it.

`workflow-effects.test.ts` has a documented parallel-execution timing flake that passes in
isolation.

Verified on this machine 2026-08-03: Node v22.20.0, pnpm 11.9.0, git 2.43.0,
`@zed-industries/claude-code-acp@0.16.2`, `@zed-industries/agent-client-protocol@0.4.5`,
`@agentclientprotocol/codex-acp@1.4.0`. All three ACP packages are pinned exactly — do not
bump them casually; M0 found two places where the SDK's types disagree with the adapter's real
output, and the Codex tests reproduce that adapter's real 1.4.0 shapes. Adapter selection
lives in `packages/server/src/agent/kinds/`, keyed by `projects.agentKind`.

## The spec is binding

[`docs/spec.md`](docs/spec.md) §2 locks fifteen product decisions and §1 lists the non-goals.
**A deviation requires amending the spec first** — if a task implies a different framework, a
different isolation model, telemetry, gamification, an orchestrator role, or anything §1 names
as out of scope, stop and raise it rather than implementing it. Twenty-four amendments exist
and are summarised in §13; twenty-three are in force, A23 (GitHub account linking) is reserved
and unimplemented. Follow the same pattern for any further deviation: amend the spec in the
same commit as the design that justifies it, and say honestly whether it is an override, a
reinterpretation of the decision's own text, or additive scope the spec never described.

Naming is settled: **VADD everywhere** — packages `@vadd/*`, binary `vadd`, state in
`~/.vadd/`, fence tag `vadd-event`, repo config `.vadd/config.json`.

## What VADD is

A localhost web app (`npx @vadd/cli`) that wraps an existing coding agent — Claude Code or
Codex, over ACP as a child process. It is a **comprehension + verification layer**, not an
agent and not an orchestrator. Two theses drive nearly every design decision:

1. **Read 10× less text** — the UI shows structured events, not log streams. This is a unit
   test, not an aspiration: a Level 1 string over 15 words or a Level 2 block over 80 words
   fails a lint on the bundled prompt templates.
2. **"Done" means proven, not claimed** — the state machine, not the UI, makes
   `integrating → done` unreachable without a full green evidence set.

## Architecture that spans files

**Output Contract pipeline** (`packages/server/src/contract`). Agents emit ```` ```vadd-event ```` fenced JSON blocks inside their message stream. The pipeline buffers `agent_message_chunk` text (thought chunks are excluded), scans for closing fences, parses, validates against the Zod `AgentEvent` union, and emits. Zod is the single source of truth — JSON Schema is *exported* from it for prompt contracts, never hand-written twice. Fallback chain: optional one-shot Haiku extraction using the exported schema (flagged `extracted: true`) → otherwise a `status` event pointing at the raw view. Emissions persist to the existing `events` table, so SSE, the raw view, transcript export, and the eval corpus all come free. Each template's front matter declares the event types it `expects` and the ones it `permits` — permitted types are allowed but never required, are skipped by `unexpected_type`, and never satisfy a phase's contract on their own.

**Workflow machine** (`packages/core`, XState v5). Defined in `core` with `setup()`, side effects named but not implemented; the server binds them with `provide()`. One machine for Feature/Bug with a Fast Fix shortcut (guard on `mode === "fastfix"` routes `exploring → planning`; verification is *never* skipped) and an Investigation mode that adds no states. Execution is one prompt per plan task, each preceded by a `vadd-checkpoint:` commit. Snapshots persist on every transition **in the same SQLite transaction as the event append**. Only three things feed the actor: validated `AgentEvent`s, user commands, and `EVIDENCE_RESULT` — raw ACP updates never reach it. Amendments A22 and A24 add two carve-outs on top of the first of those three: a `memory_note`- or `artifact`-typed `AgentEvent` is validated exactly like any other, but `WorkflowRunner.ingest` special-cases both before `toMachineEvent` ever runs — so neither reaches the actor.

**Evidence + verification.** Resolution: repo `.vadd/config.json` if present, else auto-detection (root and depth-1 subdirectories), with per-objective DB overrides merged on top and winning field by field. `setup` runs once per worktree, at creation. EvidenceCollector runs commands via `execa` at each command's `cwd` and reconciles results against `verificationSpec`; `checks` are satisfied by an agent `evidence` event of kind `check` or a manual user tick.

**Agent context.** Every field the machine assigns must be read by some later prompt or have a recorded reason why not: the user's decision and the clarification answers are folded into the goal text, a session that has to start mid-objective gets a `preface` brief (goal, decision, plan markers, memory notes), `verify.md` carries the command results, and mode notes distinguish Fast Fix and Investigation from a standard feature. `session/load` is advertised by the pinned Claude Code adapter and deliberately still unused; the brief is its fallback.

**Layering rule:** `packages/core` is domain-only — machine, ports, schemas, policies, **no I/O**, and no `node:` import on any path a browser can reach (a test walks the real import graph to enforce this). All agent communication goes behind `AgentPort`; the ACP SDK and the adapter child process are wrapped entirely inside it, so a further agent is an adapter swap. Server is Fastify + SSE only (no WebSocket); the frontend mirrors server snapshots and performs **no client-side transitions**.

## Hard constraints

- **Zero telemetry, zero outbound network** with the summarizer key unset — a test proves this with the network disabled. The optional Anthropic summarizer uses the *user's own* key; VADD never ships or requires one. The eval gate runs with it off. Only `packages/server/src/git/remote.ts` may issue a network-capable git subcommand, and a static test enforces that.
- **Isolation is git worktrees only**, under `~/.vadd/worktrees/<projectId>/<objectiveId>`. No Docker. Worktree lifecycle must be leak-free (`git worktree list` clean after integrate/discard) — and git-level success and filesystem-level success are different facts, so assert both.
- **`strict: true`** TypeScript everywhere; Node 22 LTS (Bun was rejected for `better-sqlite3`/ACP SDK compatibility).
- State lives in `~/.vadd/` — `vadd.db` (SQLite/Drizzle), `artifacts/<objectiveId>/`, `prompts/` (user prompt overrides), `worktrees/`, `agent-profiles/`.
- Git operations use a direct CLI wrapper via `execa`, deliberately not `simple-git`.
- Localhost API, no auth — intentional, not an oversight.
- The monorepo is `packages/core`, `packages/server`, `packages/web`, `packages/cli`; twelve tables, all migrated.
- `pnpm test` runs **two Vitest projects**: `node` (everything under `packages/{core,server,cli}/test`) and `web` (jsdom, `packages/web/test`). `vitest.config.ts` pins `root` to the repo explicitly — its include globs are repo-relative, so without it a filtered `vitest run` matched nothing and passed green. The `web` glob is `*.test.{ts,tsx}`, so a pure-`.ts` test is collected like any other.

## Traps M0 paid for

Each of these cost a review finding or a wrong claim. They are not hypothetical.

- **Never spawn `npx claude-code-acp`.** With `cwd` set to a worktree — which never has `node_modules` — npx falls back to the registry and silently runs an unrelated package. Resolve the pinned adapter's bin by path (`resolveAdapterBin()`).
- **The SDK drops what it cannot parse.** `ClientSideConnection` validates `session/update` before dispatch and throws on failure, so the handler never sees it and only its own `console.error` records the loss. `relaxNotificationSchema()` works around this. Treat client-side validation on the receive path as a liability.
- **The permission policy denies every path-less tool.** `Bash`, `BashOutput`, `KillShell` carry no `locations` and no path-bearing `rawInput`, so they hit the fail-closed branch. Fixed by amendment A3's command predicate (`packages/core/src/policies/command-policy.ts`, wired into `AcpAgentPort.requestPermission` in `83aabd8`) — do not reach commands by extending the path predicate.
- **`requestPermission.toolCall.locations` is often absent**, even when the earlier `tool_call` notification for the same `toolCallId` carried them. Paths come from three sources, and an empty path set must fail closed — `[].every()` returns `true`.
- **An allow is granted once.** `allow_always` maps to `acceptEdits` in this adapter, which bypasses `requestPermission` for the rest of the session and would silently disable the policy.
- **`pnpm dev` does not forward signals.** `Ctrl-C` signals the whole process group and is fine; `kill %1` orphans the server, Vite, and any adapter.
- **Transcripts have two incompatible record shapes**, and anything exported before the dropped-update fix is lossy. See `evals/transcripts/README.md`; the M1 loader discriminates on `schemaVersion` and refuses pre-fix exports.
- **~~No browser automation exists in this environment.~~ FALSE, corrected 2026-08-25.** No automation *package* is installed, which is presumably what this meant — but `google-chrome` is on PATH (147.x), `~/.cache/ms-playwright` and `~/.cache/puppeteer` both hold chromium builds, and Node 22's global `WebSocket` makes a Chrome DevTools Protocol client a dependency-free forty lines: `scripts/browser-shot.mjs`. This claim was the stated reason every UI pass since phase 5 shipped unseen. It was first used to find a real defect in the armed confirm labels. Nothing was added to `package.json`; Playwright stays deferred. A screen shipping unseen is now a choice, not a limitation.

## Traps Task 14 paid for

Found recording the real corpus, not hypothetical either.

- **The managed profile had no way to authenticate.** `ensureAgentProfile()` isolates `CLAUDE_CONFIG_DIR` from the user's real one so third-party skills can't leak in, but that also hides the OAuth session — the very first real session under the profile failed with "Authentication required" before the isolation question was even reached. Fixed in `389673b` by copying `.credentials.json` into the profile on every regeneration; isolation is about skills/plugins, not identity.
- **A Claude Code session's own env vars block its own adapter.** `claude-code-acp` refuses to start when `CLAUDECODE` is set. The server only spawns the adapter lazily, and the child inherits the *server process's* env, not the caller's — so `env -u CLAUDECODE -u CLAUDE_CODE_CHILD_SESSION -u AI_AGENT -u CLAUDE_CODE_SESSION_ID -u CLAUDE_PID -u CLAUDE_EFFORT -u CLAUDE_CODE_MAX_OUTPUT_TOKENS -u CLAUDE_CODE_BRIDGE_SESSION_ID -u CLAUDE_CODE_SSE_PORT -u CLAUDE_CODE_ENTRYPOINT -u CLAUDE_CODE_EXECPATH` in front of `pnpm dev` (or the E2E test) is enough — no separate terminal required.
- **`execute-task.md` never showed a `task_result` example.** It showed `evidence`'s JSON shape but not `task_result`'s, so the agent reliably invented the wrong fields (`status`/`headline`/`summary` instead of `taskId`/`claim`/`evidenceRefs`) and hit a schema `contract_violation` on every real execute-task turn. Fixed in `77f13f1`; affected transcripts re-recorded in `2e7c91f`.
- **A worktree's `docker compose exec` runs against the wrong checkout.** The corpus repository (a Laravel/Sail app) bind-mounts its the *main* checkout into Sail, not a VADD worktree — a worktree-scoped agent that reaches for `docker compose exec` is operating on code it didn't write. Worked around for corpus recording by symlinking `vendor`/`node_modules` and pointing a copied `.env` at the Sail containers' host-exposed ports directly (bypassing Docker entirely); `setup` commands (phase 4) are the real fix.
- **The eval corpus is turn-indexed, so anything turn-opening invalidates all 40 labels.** `loadTranscript` opens a turn on `prompt_sent` alone; a `prompt_cancelled` is turn-closing. That is why A4's repair is emitted as `repair_prompt_sent` inside the open turn, and why a cancelled turn means discarding and re-recording that whole objective rather than re-prompting it.
- **A corpus recorded across a pipeline change measures neither version.** Two contract fixes landed mid-recording from a concurrent session (`11e35d4`, `0180334`), and the resulting replay-vs-live divergence cost hours to diagnose because transcripts recorded what the agent said and not what parsed it. Confirm a clean tree and note HEAD before recording; phase 2b's `recordedUnder` stamp makes it visible afterwards.
- **Zod's length caps and thorough reasoning are in tension.** `decision_needed` options (`verification` ≤120 chars, `pros`/`cons` items ≤100 each) and `evidence.summary` items (≤100 chars) were exceeded routinely across the real corpus whenever the agent reasoned carefully. Left as-is — this is real signal for the gate, not a bug — but expect it to recur and possibly cap achievable recall.

## Traps phase 3 paid for

All four were found by running the thing, not by reading it. The first two were invisible to the unit tests that existed at the time.

- **Test setup can hide a missing production step.** `runTurn` requires an already-live agent session (`agents.get`, throwing otherwise); the prompt *route* calls `ensure()` first, but the machine's `sendPrompt` did not — so every machine-driven objective failed its very first turn into `paused`. Both `workflow-effects.test.ts` and `workflow-runner.test.ts` called `agents.ensure()` in their own setup, which made the gap invisible. The fix is guarded by `agents.get()` rather than always awaiting: an unconditional `await` defers `prompt()` by a microtask, and every turn-driving test settles the fake prompt synchronously after `send()`.
- **`PAUSE` has to stop the turn, not just the machine.** Without that, `RESUME` re-entered a state whose entry sends a prompt, `runTurn` refused with "a turn is already in flight", and the objective bounced straight back to `paused` — pause was unusable in exactly the situation it exists for. `cancelOpenTurn()` is shared by the `cancel` route and the runner's `paused` entry.
- **`createActor` does not reject a snapshot it cannot restore.** It returns an actor whose state value is `undefined` and then throws from xstate's own scheduler **asynchronously**, outside any caller's `try`/`catch` — an uncaught exception on an actor that already looked resumed. `WorkflowRunner.resume` validates `value` against `MACHINE_STATES` up front so one corrupt row cannot abort boot rehydration or take the process with it.
- **A `kill -9` orphans the adapter child.** Verified by hand: graceful shutdown stops it, a hard crash does not, because nothing records the child's pid. Design §12 requires "no orphan adapter process" after a crash-and-reboot, so this is still open. **Related trap:** `pgrep -f "tsx src/index.ts"` matches the wrapper shells, not the node process that actually holds the port — the first kill in that session silently did nothing and the run had to be redone. Confirm a server is dead by checking the listener (`ss -tlnp | grep <port>`), never by the absence of a pattern match.
- **Deleting an objective now touches six tables.** `machine_snapshots`, `decisions`, `plan_tasks` and `evidence_items` all carry a foreign key on `objectives.id` with no cascade. `integrate: discard` cleared only `agent_sessions`, so against the real server it removed the worktree and *then* 500'd on the constraint, leaving a row pointing at a directory that no longer existed. The deletes now run in one transaction, `evidence_items` first (it also references `plan_tasks`).

## Traps phase 4 paid for

- **`execa`'s `timeout` and `cancelSignal` reach the shell, not the suite.** Both signal the process VADD spawned, and a dying shell does not take `phpunit` — or `vitest`, or `sleep` — with it. The survivor also holds the output pipe open, so `await` on the subprocess resolves only when the command finishes *naturally*: `sleep 5` under a 1s timeout measured 5006ms and left the `sleep` running, which makes `timeoutSec` decorative and a `PAUSE` mid-suite a lie. `verification/run-command.ts` spawns `detached: true` and kills the process **group** (`process.kill(-pid)`), SIGTERM then SIGKILL after a grace period: 1004ms, nothing left behind. Both `runSetup` and the collector go through it; a test pins the bound itself, not just the resulting `fail` status.
- **A `VerificationSpec` cannot serve as its own override.** `CreateObjectiveBody.verificationOverrides` took the full schema, whose zod defaults fill `setup`/`commands`/`checks` with `[]` — so an override meaning "raise the timeout" arrived carrying three empty arrays, and `mergeSpec`'s leaf replacement then erased everything config or detection had just found. `VerificationOverride` (every leaf optional, absent meaning "no opinion") is the fix; a caller supplying a whole spec still parses.
- **drizzle-kit emits `?` placeholders for a `sql.join`-built CHECK.** `0002_verification.sql` came out with `status in (?, ?, …)` — nineteen bound parameters in a DDL statement that never gets any. Hand-substitute the literals, following `0001_workflow_machine.sql`, which needed exactly the same fix and is the reason to check the generated file every time rather than trusting it.
- **A bare worktree cannot run the repo's own suite, and pnpm makes it worse.** Verified by hand: a fresh worktree of this repo with only a root `node_modules` symlink still failed with `Cannot find package 'zod'`, because pnpm workspaces resolve through *per-package* `node_modules` too. This is the same class of problem as the vendored-dependency trap above, and it is why `setup` moved from "before the first verification" to worktree creation — an agent asked to work test-first cannot run a test otherwise.
- **`setup_failed` is deliberately not swept by `reconcileOnBoot`.** Unlike `creating`, the row owns the `evidence_items` row carrying the failure log; deleting it would lose the diagnostic and trip the same foreign key that broke `integrate: discard` in phase 3. `reconcileOnBoot` selects only `creating`, and a test now pins that rather than leaving it to a comment.

## Traps phase 5 paid for

- **`actor.getSnapshot().can(event)` tells you a transition exists — never that the guard you care about passed.** This is the general form, and it bit twice in one phase before being stated this way. `can()` resolves transitions from the state *value* alone: it ignores actor `status`, so it answers true on an already-terminal actor (hence `abandon` needed an explicit `status === 'done'` check beside it), **and** it answers true whenever *any* branch of a transition array is takeable — so `integrating`'s `INTEGRATE`, whose array ends in an unguarded `{ target: 'paused' }`, is always "can". Gating destructive work on `can(INTEGRATE)` therefore ran the squash and the worktree removal on unproven objectives and returned 2xx. If a guard is what matters, **evaluate the guard**, not `can()`. The route now calls `evidenceComplete` against current DB evidence before touching git.
- **A drizzle-kit table rebuild's `INSERT ... SELECT` can reference brand-new columns from the *old* table**, which does not have them. SQLite can't always add a `CHECK` in place, so drizzle-kit rebuilds `objectives` wholesale — create-new, copy, drop-old, rename — and the generated copy step named `base_sha` and `integrate_action` in the `SELECT` half, against a table that only gains those columns in the *new* half. Failed at `createDb()` with `no such column: "base_sha"`. `0001_workflow_machine.sql` is the right precedent: substitute a literal (`NULL`) for a new column in the old-table `SELECT`, the same way the already-known `?`-placeholder-in-a-CHECK trap gets hand-fixed. The two arrive together in one generated file — check the whole thing, not just the `CHECK` clause.
- **Deleting a generated migration `.sql` file does not free its slot.** `drizzle-kit generate` numbers migrations from `meta/_journal.json`, not from what `.sql` files exist on disk — deleting `0004_foo.sql` by hand and regenerating still produces `0005_...`, silently skipping a number, unless `meta/_journal.json` and the matching `meta/*_snapshot.json` are rolled back too. An 0004 stray appeared this way before the cleanup was done properly.
- **`actor.getSnapshot().can(event)` does not return `false` on an already-terminal xstate actor.** It resolves transitions from the state *value* alone and never consults `status`; a `CANCEL` declared on the machine's root `on:` is inherited by every leaf state, including the final ones, so `can({type:'CANCEL'})` answers `true` on an objective that is already `done`, `cancelled` or `failed`. A second `abandon` on an already-terminal objective needed an explicit `actor.getSnapshot().status === 'done'` check alongside `can()` — checked at the source level against xstate 5.20.1, not inferred from behaviour. `paused` is non-final, so a legitimate abandon from `paused` is not blocked by the same guard.
- **`child.killed` and `child.exitCode` never reflect a kill delivered by bare pid** — only `child.signalCode` does. `killed` is `true` only after that *specific* `ChildProcess` instance's own `.kill()` method was called; `reconcileOnBoot` holds nothing but a number read back from the database, so it can only call `process.kill(pid, 'SIGKILL')`, which the OS delivers directly and which the `ChildProcess` wrapper never learns about through `killed`. `exitCode` also stays `null` on a signal death — `signalCode` is the field that carries `'SIGKILL'`. A test polling `child.killed || child.exitCode !== null` to observe a kill could never pass; the corrected predicate is `child.exitCode !== null || child.signalCode !== null`, confirmed against a real spawned-and-killed child on Node v22.20.0 with `process.kill(pid, 0)` throwing `ESRCH` afterward as independent proof the process was really gone.
- **A live `claude-code-acp` child does not necessarily outlive a `kill -9` on its parent long enough to be "orphaned" in a testable way.** Verified by hand, twice, against a real adapter session: a `kill -9` on the server process does not itself signal the child (different pid, not a process-group kill), and the child was observed still alive in the instant immediately after — but in both trials it exited on its own within roughly 500ms, apparently on noticing its stdio pipe to the dead parent close, well before any reboot or reconciliation ran. This means the original "orphan survives until reboot" scenario is timing-dependent on what the child is doing when its parent dies: a short tool call finishes and the next stdio write fails fast; a longer-blocking one (a real test suite, not a quick `Read`) would not attempt that write until it finishes, and would stay orphaned for that whole window. `reconcileOnBoot`'s "already gone" branch is now confirmed live; its actual kill-a-still-alive-process branch is not.
- **CLOSED.** The web Vitest project's glob was `*.test.tsx` only, and a pure-`.ts` unit test (no JSX) placed in `packages/web/test/` was not collected at all — the suite went green by never running it, not by passing it. `focus-primary.test.tsx` carried a `.tsx` extension for exactly this reason despite containing no JSX itself. Fixed in `577c090`: the glob is now `*.test.{ts,tsx}`, so a pure-`.ts` test is collected like any other. The `.tsx`-naming workaround is no longer necessary — `state-color.test.ts` (added by the M2 shadcn visual pass, `8981778`) is a real `.ts` test file and is collected under the widened glob without needing it.

## Traps phase 6 paid for

- **`PRAGMA foreign_keys` is a no-op inside a transaction, and drizzle wraps the whole pending migration batch in one.** Every `PRAGMA foreign_keys=OFF` drizzle-kit emits at the top of a table-rebuild migration is therefore inert: `0001`, `0002` and `0003` all rebuild `objectives` (create `__new_objectives`, copy, `DROP TABLE objectives`, rename), and that DROP is a foreign-key violation for every `agent_sessions` row — `objective_id` is `NOT NULL` with no cascade. Enforcement stayed on, the DROP failed with `FOREIGN KEY constraint failed`, and **no installation with a non-empty `agent_sessions` could boot after upgrading**. It shipped because every test migrates a fresh, empty database, where the DROP has no child rows to violate; a migration test that does not populate the parent table proves nothing. Unlike the other two drizzle-kit traps this is **not** fixed in the `.sql` file — `createDb` sets the pragma outside drizzle's transaction, then runs `PRAGMA foreign_key_check` (SQLite's own step 11) before re-enabling, and only when migrations actually applied, so a normal boot can never be blocked by it. `PRAGMA defer_foreign_keys` is not an alternative and was measured failing identically: `DROP TABLE`'s implicit delete is checked immediately, not deferred to COMMIT.

- **`git worktree remove --force` deletes the `.git` link file before it finishes the recursive delete, and prune then hides the wreckage.** If the delete fails partway — in practice a `backend/vendor` owned by `root:root`, written by an in-container `composer install`, which this user cannot unlink — git has *already* dropped the admin entry, and the missing link file is exactly what makes `worktree prune` deregister it. `removeWorktree`'s post-condition asked only whether the path was still **registered**, so it saw a clean list and returned success while the files stayed on disk: the doc comment promised "a loud `EGIT` failure ... a permissions error" and delivered the opposite against that very case. It leaked ~1.7GB across five directories under `~/.vadd/worktrees/`, two of them from a cleanup that reported 26/26 success, and it made spec §10's leak-free release gate unobservable — the check structurally could not see the leak it existed to catch. Git-level success and filesystem-level success are different facts; assert both (`existsSync` on the path, `EGIT` naming the likely root-owned cause). Reproducible without root: `chmod 555` a directory containing a file, since unlink is authorised by the containing directory, not the file.

- **A positional id in a globally-keyed column is a one-objective-per-database bug, and the single-objective test suite could never see it.** `plan_tasks.id` is `text PRIMARY KEY`, and the machine wrote the task's *ordinal* into it — `'0'`, `'1'`, `'2'` — which is unique inside one objective and unique nowhere else. The second objective ever to reach `planning` failed `recordPlan` with `UNIQUE constraint failed: plan_tasks.id`; the action swallowed the error, so the machine walked on to `awaitingPlanApproval` and offered the user a plan with **no rows behind it**, and its `checkpoint` write — addressed by `id` alone, unscoped by objective — then landed on the *first* objective's row. Three separate defects, one root cause, and every one of them invisible to `workflow-effects.test.ts`, which drives exactly one objective. Ids are `planTaskId(objectiveId, ord)` now, with a `UNIQUE(objective_id, ord)` index making the invariant structural rather than a convention the id helper is trusted to keep; a composite primary key was rejected because `evidence_items.task_id` is a single-column foreign key onto this one. `recordPlan` sends `TURN_FAILED` on a refused insert instead of returning quietly. **The general rule: a fixture with one of the thing under test cannot show you a collision between two of them.**

- **`policy.protectedGlobs` was resolved, merged, persisted and read by nothing at all.** Spec §6's field had no enforcement point anywhere in the codebase — grep found it only in the schema, the resolution merge, and their tests — so the exit run's `backend/.env*` entry did not stop amendment A1's `setup` from rewriting the *tracked* `backend/.env.testing` (the port remap the corpus-recording traps prescribe), `git add -A` from sweeping it into every `vadd-checkpoint:` commit, or `integrate: commit`'s squash from carrying it onto the branch. Merging that would have broken every other developer's Docker workflow. The fix is in the squash, not in `setup`: a setup command that modifies a tracked file is sometimes the only way to make a worktree runnable, and "arbitrary shell must not touch tracked files" is not a rule VADD can enforce anyway — whereas "this squash carries no protected path" is decidable at exactly the moment it matters. `runIntegration` un-stages every protected path back to `baseSha` after the `reset --soft` (which also drops a *new* protected path from the index, since it did not exist at base), and emits `integrate_protected_excluded` naming them, because a squash that silently omits a file the agent believed it changed is the same class of lie as a dropped event. **A config field with no reader is not a policy — it is a comment that costs a migration.**

- **`pnpm vitest run -t "<name>"` with a name that matches nothing exits 0 with every test skipped, and reads exactly like a pass.** The phase 6 DoD walk guessed a test name (`-t "reading budget"`) that did not exist: 63 files and 576 tests **skipped**, exit 0, no error. Only an agent that read the skip count caught it — the real test is `every example block in every bundled template is valid and within budget`. Any check driven by `-t` must assert that tests actually **ran** (`Tests N passed`), never merely that the command exited 0. The same shape as the gate's own rule that a green run over nothing is worse than a red one.

- **`pgrep -f "artisan test"` matches the polling command's own cmdline.** A `bash -c` loop that greps for a pattern contains that pattern, so `pgrep -f` finds itself and reports the process as running forever. Use the bracket trick — `pgrep -f "art[i]san test"` — which matches the target's literal text but not the pattern as written. `pkill -f` is the same trap with teeth: the invoking shell's own command line contains the pattern, so `pkill -f "tsx packages/server/src/index.ts"` kills the shell that ran it (exit 144) and may or may not reach the server. Bracket the pattern, or read the pid off `ss -tlnp` and kill that. Exactly the same family as the older `pgrep -f "tsx src/index.ts"` trap: `pgrep` answers a question about *command lines*, not about the process you have in mind, and both failure directions (matching a wrapper, matching yourself) look like a confident answer.

- **`cp -al` silently drops root-owned files under `fs.protected_hardlinks=1`.** ~1,793 files in the corpus repository's `backend/vendor` were `root:root`; the kernel refuses a hard link to a file you do not own, and `cp -al` does not fail loudly on it — the worktree comes out looking populated and missing pieces. A `cp -a --no-clobber` fallback pass after the link pass is what makes the recipe complete; the project's standing "hard-link vendor, never symlink" note is incomplete without it. Related, and the reason phase 6 declined to link `node_modules` at all: hard-linking a root-owned tree into every worktree is what produces the unremovable orphans of the `removeWorktree` trap above. Link only what the commands actually need, and prove the need by running them without it.

## Traps packaging paid for

- **`process.argv[1] === import.meta.filename` never matches once Node is invoked through an npm-installed `bin` symlink.** `packages/cli/src/bin.ts`'s original "am I the entry point" guard compared the two directly, which holds for `node dist/bin.js` run straight from the build output but not for the real install path npm actually creates — the packaged binary would have silently done nothing for every real user, found only by Task 6's smoke test actually installing and running it. Fixed by extracting a zero-side-effect `resolve-defaults.ts` and making `bin.ts` an unconditional script with no self-identity check at all.
- **esbuild's `banner` option duplicates a shebang that's already in the entry file's own source.** `bin.ts` carries its own leading `#!/usr/bin/env node`, and esbuild auto-detects and preserves an entry file's own shebang in its output — adding a `banner` on top of that put the line in twice and crashed `dist/bin.js` with a `SyntaxError` on the very first `node dist/bin.js`, confirmed by hand before removing the banner (`packages/cli/scripts/build.ts`).
- **`spawn()` reports `ENOENT` asynchronously via an `'error'` event, not a synchronous throw**, so a plain `try`/`catch` wrapped around the `spawn()` call itself never catches it — an un-listened `'error'` event on the returned `ChildProcess` would crash the whole server process instead of just failing to open a browser. `packages/server/src/boot/open-browser.ts` registers a no-op `child.on('error', ...)` handler alongside the `try`/`catch` for exactly this reason; the `try`/`catch` alone only covers a `spawn()` that throws synchronously (an unresolvable command on some platforms), a different failure mode from the async one.
- **esbuild's `packages: 'external'` option also externalizes unpublished workspace packages, not just real npm dependencies.** Tried first for `packages/cli/scripts/build.ts`'s server bundle, it marked *every* bare-specifier import external — including `@vadd/core`, a plain `node_modules` symlink inside the monorepo with no tsconfig path mapping to resolve it outside — so the bundled `server.js` kept an unresolvable `import "@vadd/core"` and crashed with `ERR_MODULE_NOT_FOUND` on the first run outside the monorepo. Fixed by passing an explicit `external` list built from `packages/cli/package.json`'s own real `dependencies` (the native `better-sqlite3` and the by-real-path-resolved `@zed-industries/claude-code-acp` among them), letting `@vadd/core` bundle into `server.js` like any other first-party source.

## Traps the web redesign paid for

- **Vite statically special-cases the literal pattern `new URL('<literal>', import.meta.url)`** as its asset-URL-import shorthand, and rewrites it — under this project's `web` Vitest project (jsdom environment, Vite's transform pipeline), that rewrite resolves the URL against jsdom's default document location (`http://localhost/`) instead of the real module path, and the literal form threw `TypeError: The URL must be of scheme file`. Binding `import.meta.url` to an intermediate variable first (`const here = import.meta.url; new URL('../src', here)`) defeats Vite's static pattern match — `import.meta.url` alone is untouched and correctly reports a real `file://` URL — and restores the real path. Found writing `no-raw-palette.test.ts` (`5f15a5a`), which needs a real filesystem path to walk `packages/web/src`.
- **A dialog mounted unconditionally never unmounts, so its `useState` survives close and reopen.** `AppShell` mounts `NewProjectDialog` and `NewObjectiveDialog` once and toggles Radix's own `open` prop rather than conditionally rendering them — the idiomatic shadcn/Radix pattern, and correct for animation, but it means neither dialog's local state resets on its own the way a freshly-mounted component's would. A failed submit against `NewProjectDialog` left its error message sitting over a blank form the next time it opened (`784e6c5`); `NewObjectiveDialog` was built with the same guard from the start once the pattern was known (`804e76e`). Both now reset via a `useEffect` keyed on `open` that clears every local field when the dialog transitions to open. The general form: a component whose *lifetime* is longer than its *visible* lifetime cannot use mount as its reset signal — it needs an explicit one tied to the thing that actually recurs.
- Also worth recording, not a trap so much as the evidence for building the automated check in the first place: `no-raw-palette.test.ts`'s whole-tree walk caught `evidence/DiffViewer.tsx` still carrying a raw palette class — a file the plan's own hand-written list of surfaces to fix had missed. A hand-maintained list of "the files that need fixing" is exactly the kind of thing a plan author can miss and a full-tree scan cannot.

## Traps the first browser render paid for

The app was opened in a real browser for the first time on 2026-08-23, by the user, after the standing "no browser automation exists in this environment" gap had been carried since M0. It found a crash on the first screen that reached it — which is the point of the entry below.

- **A barrel is browser-hostile the moment a browser imports it for value, and the `web` Vitest project structurally cannot tell you.** `06710f5` gave `DecisionCard.tsx` the first *value* import of `@vadd/core` in `packages/web` (`primary.ts`'s is `import type`, erased at compile, which is why nothing broke earlier). A barrel re-exports eagerly, so loading it evaluates every module it names — including `policies/command-policy.js`, the one file in `packages/core/src` that imports a `node:` builtin, reached both directly *and* again through `policies/verification-resolution.js`. Vite substitutes a stub that throws on any property access, so the barrel threw before `scoreOption` was ever reached: `Cannot access "node:path.isAbsolute" in client code`, taking down every page that renders the Decision Card. **jsdom cannot catch this** — `environment: 'jsdom'` still runs inside Node, where `node:path` resolves normally; jsdom simulates the DOM, not the browser's module environment. The suite was green over the broken code. Fixed at the boundary that is actually wrong — a browser pulling in a server-oriented domain barrel — with a subpath export and a deep import (`@vadd/core/scoring/option-priority.js`; that module has no imports of its own). Making the whole barrel browser-safe was tried first and rejected: `verification-resolution.ts` reaches `command-policy` independently, so it would have meant severing a real domain dependency or hand-rewriting a security predicate's path math to appease a bundler. `packages/web/test/no-node-builtins.test.ts` now walks the real import graph from every file in `packages/web/src` — following relative, `@/` and `@vadd/core` specifiers, skipping erased `import type` lines — and asserts nothing reaches a `node:` builtin; it was confirmed to *fail* on the original import before being trusted. Fixed in `a17a8e7`. **The general rule: any invariant that only holds in a browser is unfalsifiable under jsdom, and needs a static check instead.**
- **Not every console error is a defect, and a 409 on `/diff` is the current example.** `GET /api/objectives/:id/diff` 409s with "no worktree or no recorded base commit" for any objective whose `baseSha` is null, and `DiffList.tsx` already handles it correctly (`.catch` → `setError` → render nothing); the console line is DevTools logging a non-2xx response, which it does whether or not JS handles it, with the React stack merely attributing the fetch call site. The underlying cause is data, not code: `objectives.baseSha` arrived with amendment A8 on 2026-08-16 and is written at creation from `createWorktree`, so it is null on every objective created before then and nothing backfills it. The live `~/.vadd/vadd.db` splits exactly on that date — four pre-A8 objectives with null, one post-A8 with it set. **Consequence for anyone driving the existing demo data: a pre-A8 objective can never be integrated with `commit`** — `integrate.ts` refuses it with a message saying to use `keep` — so a hand-driven demo on one of those four rows will hit a wall at the last step. Create a fresh objective instead.

## Traps Pass C paid for

Only what was actually observed while building the remote surface — not what a mitigation was designed in advance to avoid.

- **`GIT_TERMINAL_PROMPT=0` does not prevent a credential hang.** Probed against a real local server answering `401 WWW-Authenticate`, with an askpass helper that sleeps: `GIT_TERMINAL_PROMPT=0` set exactly as the design originally prescribed still **hung**, killed at 10s. Git consults `GIT_ASKPASS` before it ever considers a terminal prompt, an askpass helper needs no TTY at all (so piped stdio is irrelevant), and `execa` merges its `env` option with `process.env` rather than replacing it, so a user's own `GIT_ASKPASS` — GNOME keyring, Git Credential Manager, an IDE integration, all common — is inherited into the child regardless of what VADD sets. `GIT_ASKPASS: ''` was measured sufficient **alone**, even against a repository with `core.askPass` set in its own git config.
- **This git already refuses an unconfigured divergent pull outright — which masked `--ff-only`'s own role until it was deliberately unmasked.** Building the "drops `--ff-only`, expect a stop" fixture, the divergence itself was unreachable without first setting `pull.rebase false` in the fixture's git config; without that, git refuses the pull before `--ff-only` ever enters the picture. Once unmasked, dropping `--ff-only` produced a silent clean merge (`Merge made by the 'ort' strategy`, exit 0, HEAD advanced, no error), not the conflict originally assumed.
- **`git pull --ff-only <remote>` with no upstream configured genuinely refuses**, so `pullFastForward` resolves and passes the branch explicitly (`git pull --ff-only <remote> <branch>`) rather than relying on an upstream the test fixtures never set — measured by removing the branch argument and watching the bare form fail.
- **`rev-parse @{upstream}` resolves by ref lookup, while `rev-list` walks objects — and deleting a loose object splits the two.** This is what made a genuinely discriminating `aheadBehind` mutation-check possible: a repro that only deletes a remote-tracking *ref* fails `rev-parse` before `rev-list` is ever reached, so the two calls could not be told apart. Corrupting a loose object instead lets `rev-parse` succeed (it never touches object content) while `rev-list` fails (it has to walk the object it can't read), proving the `try`/`catch` guard actually covers the second call and not just the first.
- **`--upload-pack='sleep 30'` does not hang this machine's git, and a `git://` fallback spawns no child process at all — so neither could test a process-group kill.** A local-filesystem-transport fetch passes the remote's path as an extra argument to the upload-pack command line, and GNU `sleep` rejects the extra argument (`sleep: invalid time interval '../bare'`) and exits in ~4ms rather than blocking. The design's own named alternative, a black-holed `git://10.255.255.1/x.git` address, has the opposite problem: that transport is a single TCP connect performed by the `git` process itself, with no child spawned, so killing only the leader "passes" the test without ever exercising the process-group kill `killGroup` exists for. The test that actually discriminates uses a local wrapper script that ignores its arguments and `exec`s `sleep 30` in their place, reproducing a real transport-spawned grandchild — confirmed by hand that killing only the `git` leader pid leaves `sleep 30` running as an orphan holding the output pipe open (`await child` never resolves), while the negative-pid group kill reaches it and the process actually dies.

## Traps the git surface's first live run paid for

The 23 git routes had only ever been driven through `app.inject`. Driving them against a real running server found all three of these; none was visible to the suite.

- **A test can encode reasoning that running the thing overturns, and it will keep the defect green.** `git-mutate-wrapper.test.ts` asserted that a push "must not silently consume the undo step the previous local operation earned" — a plausible sentence, written in advance, that made the desync a *requirement*. The live run showed the record does not become wrong at the moment of the push so much as stop being purely local: `reset --hard beforeSha` no longer restores a state, it creates a divergence with the remote just written to. A test whose comment argues for its assertion is not thereby verified; it is only more expensive to overturn. **Related, and the reason the defect survived review:** the final whole-branch review saw this and recorded it Minor because the console hides the button. An invariant that lives only in the client is not an invariant — this project has had to correct exactly that once before (A15's `integrate: commit`, refused in `IntegrationChooser` while the route still accepted it).
- **A `safeParse(...) ? x : fallback` collapses two different facts, and on a policy read it collapses them in the dangerous direction.** `VerificationSpec.safeParse(objective.verificationSpec).success ? …policy.protectedGlobs : []` answers "no protected paths" for both "this objective declares none" and "VADD cannot read what this objective protects". The second is a fail-open, and it is invisible where it matters: the commit reports `excludedPaths: []`, which is exactly what a working exclusion that found nothing reports. Note also that `safeParse(null)` *fails* — so the legitimate no-spec case has to be answered before the parse, not after it, or fixing the fail-open turns every unresolved objective into a refusal.
- **A refusal computed after the first mutating step is not a refusal.** The fail-open fix was first written inside `excludeProtected`, which runs after `git add -A` and `reset --soft baseSha` — so `integrate: commit` would have returned `{ ok: false }` having already moved the branch back to base with everything staged. The test asserting the branch had not moved is what caught it. Read the inputs a guard needs before touching the worktree, not at the point the value is consumed.

## Traps the stray worktrees pass paid for

All three found by building the thing, not by reasoning about it in advance.

- **`git worktree list` cannot show the leak that motivated the guard against it.** The topology route builds its `worktrees` array entirely from `listWorktreesDetailed()`, so a directory git does not register reaches no screen. The phase 6 leak was exactly that shape — `git worktree remove --force` deletes the `.git` link file before finishing the recursive delete, and the missing link file is what makes `prune` deregister the entry. CLAUDE.md's own Pass A row claimed the console was "the first surface able to show one by path"; it could show an `orphan` (a worktree git still registers with no claiming row) and not this — the claim is corrected above.
- **A defence-in-depth guard's test usually passes for the other guard's reason.** Task 3's root-containment check (`isUnder`) could not be pinned by the obvious fixture, because the strays-membership guard already refuses everything outside the root first — `onDisk` comes from a `readdir` OF that root, so nothing outside it is ever a candidate stray. The test only discriminates on the one input that reaches guard 2 alone: an objective's `worktreePath` pointing outside the worktree root, gone from disk, reported `vanished` (so it IS in the strays list) and refused only by `isUnder`. A redundant guard is worth having and is exactly the kind whose test silently proves nothing until it is built this deliberately.
- **`fs.rm`'s `force` suppresses `ENOENT` only.** Every other failure — `EACCES` among them — throws, so a post-condition placed after the `rm` call cannot be reached by any permission-denied fixture; the `catch` returns 500 before `existsSync` is ever consulted. The post-condition stays in as insurance against a delete that reports success without actually removing anything, but its own test cannot be the thing proving that insurance fires — worth knowing before writing a test that appears to pin one.

## Traps the card artifacts pass paid for

- **Zod 3's `discriminatedUnion` only accepts bare objects as options — `.refine()` on one option doesn't compile, and even where a refinement does apply it's invisible to `zod-to-json-schema`.** Spec §3.1's own worked snippet for `Card`'s row-width and line-cap cross-field rules called `.refine()` per card kind before combining them into the union; that isn't valid Zod 3 (confirmed by writing it and watching it fail to type-check, not by reading the docs first). The fix is one `.superRefine()` on the whole `Card` union instead of per-option refinements — but that has its own cost worth knowing in advance: the JSON Schema export (`pnpm schema:export`, which feeds the agent's own contract reference) ignores refinements entirely, so a `superRefine` rule reaches the agent only through template prose and the schema rejection message it gets back on a bad emission, never through the structured "shape" the agent is shown. Any future Zod union carrying a cross-field rule in this codebase will hit the same two facts.
- **A `useState(propValue)` collapse toggle only reads its prop once, at mount — a later prop change from a sibling control has no visible effect on an already-rendered child, and no test that only mounts fresh catches it.** `CardFrame`'s `const [collapsed, setCollapsed] = useState(defaultCollapsed)` looked correct and was covered by a passing test (`ArtifactBlock` mounted directly with `lowEnergy={true}`) — but a *live* Low Energy Mode toggle, clicked while the Decision Card's cards were already on screen, had no effect at all: the route doesn't remount, so `defaultCollapsed` changes but `useState`'s locked-in initial value doesn't. Found only by driving the real app in a browser and clicking the actual toggle, not by any unit test — the existing test suite genuinely could not have caught this, since every one of its renders passed `lowEnergy` as a fixed prop at mount rather than flipping it after. Fixed with a `useEffect(() => setCollapsed(defaultCollapsed), [defaultCollapsed])` re-sync (`73da54e`). The general form: any `useState` seeded from a prop that a sibling control can change later needs an explicit re-sync effect, or a test that mounts once and then changes the prop (RTL's `rerender`) to prove it — mounting fresh with the new value every time hides the bug completely.

## Traps the UI/UX rework paid for

Found by the closing browser pass at three widths, and by tests that refused a design assumption. The suite was green over every one of the first four.

- **Radix `Slot` joins `className`s as strings, so a function `className` on the child is stringified to its source and every class in it is lost.** `TooltipTrigger asChild` around a react-router `NavLink` whose `className={({ isActive }) => …}` produced a link with no `relative`, and the absolutely-positioned needs-you badge anchored itself to the sticky `<aside>` instead — visible only at 820px, where the icon rail renders. jsdom cannot see a position. Give a slotted child a string className and style the active state with `aria-[current=page]:` variants, which NavLink sets itself.
- **`layoutCommits` records a commit's own lane as open *before* it assigns the parents, so a root (or a commit whose first parent another lane was already waiting for) still carries a straight own-lane segment in `rails`.** The glyph rail never showed this because the dot overwrote that cell. An SVG gutter draws it as a rail below a root. The layout now returns `continues` (`open[lane] !== null` after assignment), the gutter skips the own-lane segment when it is false, and the next row filters that segment out of what "arrives" — three places, one fact.
- **Counting evidence history as if it were the current set.** `groupEvidence` deliberately keeps every run of a non-check row (a suite that went red then green shows both), and a *count* of that reported a done objective as "14/22 required · 8 not passing". `currentRequired()` — newest row per `commandId`, the way the server's `evidenceComplete` guard reads the set — is what a tile may count; the rows keep the history.
- **`fitView` enlarges as well as shrinks.** Two map nodes were zoomed to fill a 1200px canvas; `fitViewOptions={{ maxZoom: 1 }}`.
- **`paused` is an attention tone, not an idle one** (M2 visual pass §3: a paused objective is the user's to resume). The design grouped it under "Paused" beside `idle`; the grouping test written from the design failed against `statusFor` and the design was wrong. When a taxonomy already exists in code, the new screen reads it; it does not restate it.
- **The board tests relied on an empty projects list and a "fetch everything" fallback that no real board ever uses.** Once the list came from a project-scoped live hook, eight tests fetched nothing. A fixture that cannot happen in the product proves less than it looks; the fixtures now carry one project.

## Traps the agent context flow pass paid for

- **A field the machine assigns and no prompt reads is context the agent never gets — and the suite stays green over it.** `pendingDecisionId`, `pendingClarification` and `decisions.chosenId` each had a test proving they were *written*; none had one proving a later prompt *read* them. `DECIDE` moved to `planning` and `plan.md` carried the bare goal; `ANSWER_CLARIFICATION` nulled the question and dropped the answer; M1 design §6.5's fresh-session seed was deferred by `rehydrate.ts` to the lazy `ensure()`, which then opened a blank session with no seed at all. Single Vitest file: `pnpm vitest run <path>`; single test: add `-t "<name>"`. It exits non-zero on an unlabelled transcript or an orphan label too, so keep `evals/transcripts/*.jsonl` and `evals/labels/*.labels.json` in exact name correspondence.

For a corpus re-record, run the server as `npx tsx src/index.ts` under the `env -u` list in "Traps Task 14 paid for" — **not** `pnpm dev`, whose `tsx watch` reloads on any file touch into an `EADDRINUSE` race that has already killed one run mid-turn.

Real-adapter E2E, when credentials exist: `VADD_E2E=1 pnpm vitest run packages/server/test/e2e-real-agent.test.ts`, under the same `env -u` list (a Claude Code session's own env vars block the adapter). CI (`.github/workflows/ci.yml`) runs lint → typecheck → test → eval on every PR and push to `main`/`master`, with `VADD_E2E` unset and `pnpm eval` as `continue-on-error`.
